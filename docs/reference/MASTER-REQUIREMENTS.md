# OMINIX — Master Technical Specification

**Document Type:** Product / Architecture / Implementation Specification  
**Language:** English only  
**Target Platform:** Windows Desktop + Microsoft Word, Excel, PowerPoint  
**Primary Deliverable:** `OMINIX-Setup.exe`  
**Project Status:** Master specification for implementation and architectural approval

---

## 0. Executive Definition

OMINIX is a **native Windows AI integration and automation platform for Microsoft Office** whose primary user experience must live **inside Microsoft Excel, Microsoft Word, and Microsoft PowerPoint**.

OMINIX MUST NOT be implemented as a Local Web Application, Localhost Web UI, browser-hosted application, or HTTP-served Office workspace.

OMINIX is not a browser application, not a Chrome extension, not an Edge-hosted application, and not a generic Windows chat application. Its Office integration must be a **native Windows Office Add-in implementation** appropriate to the supported desktop Office hosts. A small local background process may exist only as infrastructure for provider routing, secure credential storage, local process communication, model orchestration, logging, and health management.

The production architecture MUST use **native inter-process communication (IPC)** rather than HTTP/HTTPS localhost as the primary Office-to-Core transport. Recommended mechanisms include Windows Named Pipes or another authenticated native IPC mechanism. HTTP localhost MUST NOT be used as the required production transport.

The core concept is:

```text
Microsoft Excel ─┐
Microsoft Word  ─┼──> Native OMINIX Office Bridge ──> Secure Native IPC ──> OMINIX Core ──> AI Providers
PowerPoint      ─┘
```

The system must enable a user to open an OMINIX workspace from inside Excel, Word, or PowerPoint; chat with an AI model; provide the AI with controlled access to the current Office application and document; and allow the AI to perform authorized operations using the native object model and APIs of that Office application.

The system must be designed as an **Office-native AI operating layer**, not as a website embedded next to Office.

# 1. Non-Negotiable Product Rules

These rules are mandatory.

## 1.1 Office-First Rule

All primary OMINIX interaction must happen **inside the Office host application**.

Supported first-class hosts:

- Microsoft Excel
- Microsoft Word
- Microsoft PowerPoint

The primary UI must be exposed through the Office Ribbon and Office task pane/workspace.

## 1.2 No Browser-Centered UX

OMINIX must not require the user to open Google Chrome, Microsoft Edge, or another browser to use the product.

A local HTTP/HTTPS endpoint may exist internally for communication between the Office Add-in and the local OMINIX Gateway, but the endpoint is infrastructure, not the user interface.

The following must NOT be the primary product experience:

- Chrome application
- Browser dashboard
- Standalone web chat
- Localhost page opened in a browser
- Browser extension used as the Office integration

## 1.3 No Separate Windows UI as the Main Workspace

A Windows tray component is allowed only as a support/infrastructure utility.

The actual OMINIX workspace, chat, model selection, Office actions, settings relevant to Office work, context controls, and agent interaction must be accessible from inside Word, Excel, and PowerPoint.

## 1.4 English-Only Internal Product

All software-visible language must be English.

This includes:

- UI labels
- Menus
- Ribbon labels
- Buttons
- Settings
- Error messages
- Logs shown to users
- Provider names where configurable
- Model metadata labels
- Installation screens
- Help text
- Tool names
- Permissions
- Agent messages generated by the product
- About section structure
- Documentation shipped with the application

Do not create Persian UI, Persian configuration keys, Persian source-code identifiers, or bilingual UI logic.

The product must be architected for localization in the future, but the production language for this project is English.

## 1.5 No Local Web Application Architecture

This is a mandatory architectural rule.

OMINIX MUST NOT be designed or shipped as: 

- a localhost web application
- a local HTTP server used as the primary Office transport
- a local HTTPS web server used as the primary Office transport
- a browser-based task pane launched from localhost
- a browser tab containing the OMINIX workspace
- a standalone web dashboard
- a web application wrapped inside a Windows shell

The following production architecture is explicitly prohibited:

```text
Office
  ↓
http://localhost:<port>
  ↓
Browser/Web Page
  ↓
OMINIX UI
```

The following production architecture is required:

```text
Excel / Word / PowerPoint
          ↓
Native OMINIX Office Add-in
          ↓
Native UI / Custom Task Pane
          ↓
Authenticated Native IPC
          ↓
OMINIX Core
          ↓
Provider / Model Layer
```

## 1.6 Native Office UI Requirement

For Windows Desktop production builds, the preferred Office integration SHALL be a **native Windows Office Add-in architecture** capable of hosting a native task pane/workspace inside Excel, Word, and PowerPoint.

The implementation SHOULD use the supported native Office desktop mechanisms for the target versions, such as VSTO/COM-based Add-ins and Custom Task Panes where appropriate.

The UI layer SHOULD be implemented with native Windows UI technologies (for example .NET/WPF or WinForms) rather than a localhost webpage.

A web runtime may only be used if a specific Office platform capability makes it unavoidable, and in that case it MUST NOT require a localhost web server, browser window, or externally navigated web page. Such an exception MUST be documented and approved as an architectural exception.

## 1.7 Native IPC Requirement

The Office Add-in and OMINIX Core MUST communicate through a secure native IPC mechanism.

Preferred order:

1. Windows Named Pipes with authenticated client/server identity
2. Another Windows-native authenticated IPC mechanism
3. Localhost HTTP/HTTPS only as an explicitly documented compatibility fallback, never as the primary architecture

The Core MUST NOT require a listening web server solely to make the Office Add-in function.

## 1.8 No Browser / No Localhost Production Dependency

A production installation MUST continue to function when: 

- Chrome is not installed
- Edge is not launched
- no browser window is open
- the user never navigates to localhost

The normal OMINIX workflow MUST begin from the Office application itself.

## 1.5 No Fake Capabilities

OMINIX must never pretend that an Office capability exists when the selected Office version or API does not support it.

Every Office capability must be checked against the host/application/API requirement level at runtime.

Unsupported operations must produce a clear English capability message and a safe fallback rather than silently failing.

## 1.6 Secure by Default

API keys, access tokens, refresh tokens, and other credentials must never be stored in plaintext in the Office Add-in source, JavaScript bundle, ordinary JSON configuration, logs, or chat history.

The Add-in should communicate with the local OMINIX Gateway; provider secrets belong in a secure local secret store.

## 1.7 One OMINIX Core, Three Office Clients

Excel, Word, and PowerPoint must not contain independent AI/provider implementations.

They are three Office-specific clients/bridges around one OMINIX Core.

```text
                 OMINIX CORE
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
   Excel Bridge   Word Bridge   PowerPoint Bridge
        │            │            │
        └────────────┼────────────┘
                     ▼
              OMINIX Gateway
                     ▼
             Provider / Model Hub
```

# 2. Product Vision

OMINIX must make an AI model behave like a highly experienced Office operator **within the permissions and APIs actually available to the application**.

The AI must be able to:

- Understand the active workbook/document/presentation.
- Read relevant Office content.
- Inspect structure and metadata that the Office API exposes.
- Work with user-selected content.
- Generate content.
- Insert or update content.
- Format content.
- Build structured Office objects.
- Analyze existing content.
- Create new content from instructions.
- Refactor or transform existing content.
- Automate multi-step Office workflows.
- Explain its actions.
- Ask for confirmation when an operation is configured as approval-required.
- Recover from tool errors when possible.
- Use fallback AI providers when the configured routing policy allows it.

The product must not claim universal access to every feature of the desktop Office object model. It must implement the maximum practical capability through the supported Office Add-in APIs and explicitly document capability boundaries.

# 4. Office Version Compatibility Strategy

A single Office.js feature set cannot be assumed to work identically across all Office generations.

Microsoft documents requirement sets/capabilities and runtime checks for Office Add-ins. The implementation must therefore use a capability matrix.

## 4.1 Compatibility Tiers

```text
Tier A — Modern Supported Office
    Microsoft 365 / supported current desktop Office
    Full OMINIX Add-in capability where APIs are supported.

Tier B — Older Office with sufficient Add-in support
    Reduced capability according to requirement sets.

Tier C — Legacy Office without required Office Add-in support
    Do not claim full embedded OMINIX support.
    Installer may report "Unsupported for native OMINIX integration".
    A standalone compatibility layer may exist only for diagnostics/admin use,
    not as a substitute for the requested Office-native workspace.
```

The project must not make a false promise of identical support from Office 2000 onward.

If legacy products do not expose the APIs required for the native architecture, the correct result is a clear compatibility report, not a browser workaround.

## 4.2 Runtime Capability Detector

At Add-in startup, detect:

- Office host
- Office version/build where available
- Platform
- Architecture where available
- Supported requirement sets
- API support
- Add-in command support
- Task pane capability
- Relevant Word/Excel/PowerPoint object-model capabilities

Store capability results in an internal runtime profile.

Example:

```json
{
  "host": "Excel",
  "platform": "Windows",
  "supportedCapabilities": {
    "taskPane": true,
    "ribbonCommands": true,
    "excelApi": true,
    "tables": true,
    "charts": true
  }
}
```

# 21. Security Architecture

## 21.1 Secrets

Store provider credentials using an OS-backed secure storage mechanism on Windows where practical.

Requirements:

- Encryption at rest
- No plaintext API keys in logs
- No API keys in chat history
- No API keys in source code
- No API keys in Office document properties
- No API keys in browser storage
- Mask credentials in UI

## 21.2 Local Gateway Security

The local Gateway must:

- Bind to localhost by default
- Reject unintended remote access
- Validate origin/host information where possible
- Authenticate local client requests using an installation/session mechanism
- Use HTTPS where required by the Office Add-in hosting model
- Use a trusted local certificate for the development/local deployment scenario when required

---

# 22. HTTPS / Local Hosting

Office Add-ins are web-based components and Microsoft strongly recommends secure HTTPS hosting; insecure add-in content can produce warnings/errors. For local development/testing, a self-signed certificate may be used when the certificate is trusted on the local machine.

OMINIX must therefore separate two concepts:

```text
Office-native UI
      ↓
Trusted local Add-in origin
      ↓
Local OMINIX Gateway
```

Do not make Chrome the hosting requirement.

The installer must automate the local certificate/setup steps required by the chosen deployment architecture.

# ARCHITECTURE UPGRADE — NATIVE OFFICE / ZERO-LOCAL-WEB PRODUCTION MODEL

## A. Objective

The purpose of this upgrade is to eliminate the current Localhost/Web architecture from the OMINIX production design. OMINIX SHALL be a native Windows-integrated Office product rather than a local website exposed through a browser or a browser-like wrapper.

## B. Required Production Topology

```text
                    WINDOWS DESKTOP
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ▼                  ▼                  ▼
     EXCEL               WORD            POWERPOINT
        │                  │                  │
        ▼                  ▼                  ▼
 Native OMINIX       Native OMINIX      Native OMINIX
 Custom Task Pane    Custom Task Pane   Custom Task Pane
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
                    Secure Native IPC
                    (Preferred: Named Pipe)
                           │
                           ▼
                    OMINIX CORE
                           │
         ┌─────────────────┼─────────────────┐
         ▼                 ▼                 ▼
   Agent Engine      Provider Hub       Security Vault
         │                 │                 │
         └─────────────────┼─────────────────┘
                           ▼
                    AI Model Layer
```

## C. What OMINIX.exe / OMINIX Core Does

The OMINIX Core process may run silently in the Windows background. It SHALL NOT present a normal browser UI.

Responsibilities include:

- Provider management
- Model routing
- Agent orchestration
- Tool execution coordination
- Secure credential access
- Context processing
- DLP policy enforcement
- Audit logging
- Job management
- Health monitoring
- Local model integration
- Native IPC endpoint
- Watchdog/self-healing

## D. What the Office Add-in Does

The Office Add-in is the actual user-facing product surface. It SHALL:

- create/open the OMINIX Ribbon commands
- open a native OMINIX Custom Task Pane inside the Office host
- display Chat
- display Models
- display Agents
- display Context controls
- display Provider selection where appropriate
- display Settings relevant to Office use
- display Approval dialogs
- display Change Preview
- display Job state
- display Verification results
- display Diagnostics
- display About and Creator/Support

## E. Prohibited Production Components

The production installer MUST NOT depend on:

- Chrome
- Edge
- Chromium startup
- browser navigation
- localhost webpage navigation
- an external web dashboard
- a local web server as the primary Office bridge
- a URL typed into a browser by the user

## F. Development Exception

A developer build MAY use a temporary local web development server when required by the development toolchain. This is a build-time convenience only.

It MUST NOT leak into the production architecture.

The production binary MUST NOT print user instructions such as:

```text
Press O to open the Task Pane in your browser.
Taskpane URL: http://localhost:3000
```

## G. Native UI Technology Decision

The implementation team MUST evaluate native Windows Office integration first. For Windows Desktop Office targets, the preferred production approach is:

```text
C# / .NET
   +
VSTO / COM Add-in
   +
Custom Task Pane
   +
WPF or WinForms UI
   +
Windows Named Pipes / secure native IPC
   +
OMINIX Core
```

A different native implementation MAY be selected only when technically justified and documented.

## H. Office Version Strategy

The native integration layer SHALL maintain an explicit compatibility matrix.

The implementation MUST distinguish:

- Office versions that support the selected native add-in architecture
- Office versions requiring reduced functionality
- Office versions requiring a legacy adapter
- Office versions that cannot support the target architecture

The project MUST NOT claim universal support for Office versions that have not been actually validated.

## I. Native IPC Security

The IPC channel MUST include:

- client authentication where available
- server identity validation
- request authorization
- message validation
- timeout handling
- cancellation
- correlation IDs
- audit logging

Sensitive credentials MUST NOT be transmitted to the Office UI unless strictly necessary.

## J. Native IPC Protocol Contract

The communication contract SHOULD be structured rather than ad-hoc strings. Example conceptual message:

```json
{
  "requestId": "...",
  "sessionId": "...",
  "officeHost": "Excel",
  "operation": "agent.execute",
  "payload": {},
  "capabilityContext": {},
  "permissionContext": {}
}
```

The exact serialization format may be JSON, MessagePack, Protocol Buffers, or another documented format. The transport itself SHALL remain native IPC in production.

## K. Native Task Pane Behavior

The OMINIX Task Pane SHALL behave like an integrated part of Office.

Example:

```text
Excel
 └── Ribbon
      └── OMINIX
           └── Custom Task Pane
                ├── Chat
                ├── Models
                ├── Agents
                ├── Context
                ├── Approvals
                ├── Jobs
                ├── Diagnostics
                └── Settings
```

The same model SHALL exist for Word and PowerPoint.

## L. Installer Requirements for Native Architecture

`OMINIX-Setup.exe` SHALL:

1. Detect supported Office installations.
2. Detect product, version, build, architecture, and installation type.
3. Select the correct native Office integration strategy.
4. Install the required OMINIX Core components.
5. Register the native Add-in with the supported Office mechanisms.
6. Register or configure the Custom Task Pane integration.
7. Configure the native IPC channel.
8. Configure secure credential storage.
9. Run Office integration diagnostics.
10. Verify that no browser is required for normal operation.
11. Provide Repair capability.
12. Provide Uninstall capability.

## M. Production Acceptance Criteria for the Zero-Local-Web Requirement

The requirement is PASSED only when all of the following are true:

```text
1. User opens Excel manually.
2. OMINIX appears in Excel.
3. User clicks OMINIX.
4. OMINIX opens inside Excel.
5. No browser opens.
6. No localhost URL is shown to the user.
7. No local web server is required for the primary workflow.
8. Chat communicates with OMINIX Core through native IPC.
9. AI can execute approved Excel tools.
10. Verification succeeds.
```

Repeat the same test for Word and PowerPoint.

## N. Hard Failure Conditions

The architecture MUST be considered non-compliant if:

- the production Task Pane is an externally opened localhost webpage
- the user must visit localhost manually
- the user must open Chrome or Edge
- the primary OMINIX UI is outside Office
- the Office Add-in depends on a web server to render its primary interface
- the production console instructs users to open OMINIX in a browser

## O. Final Architectural Statement

OMINIX is a **native Office-integrated AI automation system**.

The Office application is the user's workspace.

OMINIX Core is the background intelligence layer.

The Office Add-in is the user interface.

Native IPC is the preferred Office-to-Core communication mechanism.

A browser and a localhost web application are NOT part of the production OMINIX user experience.
